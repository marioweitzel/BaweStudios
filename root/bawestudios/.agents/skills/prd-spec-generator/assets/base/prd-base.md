# BAWE PRD BASE TEMPLATE
Version: 1.0

## PURPOSE

This template defines the canonical structure for every PRD generated by BaWeStudio.

A PRD describes WHAT must be built.

It never defines HOW it will be implemented.

Technology decisions belong to later pipeline stages.

---

# GENERATION OBJECTIVES

Every generated PRD must be:

- Complete
- Coherent
- Self-contained
- Prioritized
- Testable
- Actionable

Any downstream skill should be able to work using only this document.

---

# REQUIRED SECTIONS

## 1 Executive Summary

Describe the project in one paragraph.

Include:

- Project name
- Business goal
- Primary users
- Expected value

---

## 2 Product Vision

Describe the desired final product.

Focus on business value.

Never describe implementation.

---

## 3 Problem Statement

Explain:

Current problem

Current pain

Consequences

Expected improvement

---

## 4 Target Audience

Identify:

Primary users

Secondary users

Stakeholders

Expected user volume

---

## 5 User Personas

Describe the most representative users.

For each persona include:

Name

Goals

Frustrations

Technical level

Main actions

---

## 6 Functional Requirements

Describe every feature.

Each requirement must:

- represent one functionality
- be atomic
- be testable
- have business value

---

## 7 Non Functional Requirements

Examples:

Performance

Availability

Security

Accessibility

Localization

Scalability

Privacy

---

## 8 User Stories

Import format from:

user-stories.md

---

## 9 Main User Flows

Describe complete user journeys.

Each flow must include:

Start

Steps

End

Possible errors

---

## 10 product delivery Scope

Only essential functionality.

Must produce value immediately.

Must remain functional, professional and client-presentable.

---

## 11 Deferred Scope

Everything intentionally postponed.

---

## 12 Acceptance Criteria

Import rules from:

acceptance-criteria.md

---

## 13 Success Metrics

Examples:

Conversion

Registrations

Retention

Orders

Revenue

Daily users

Completion rate

---

## 14 Risks

Functional risks

Business risks

Technical assumptions

Dependencies

---

## 15 Out Of Scope

Everything intentionally excluded.

This section prevents feature creep.

---

# QUALITY RULES

Never invent requirements.

Never duplicate functionality.

Never mix business and implementation.

Never define APIs.

Never define database schemas.

Never define frameworks.

Never define programming languages.

Never define cloud providers.

Never define Docker.

Those belong to Architecture.

---

# VALIDATION CHECKLIST

Before finishing verify:

✔ Every feature belongs to a user need.

✔ Every story has acceptance criteria.

✔ product delivery is deployable and client-presentable.

✔ Deferred Scope is separated.

✔ No technical implementation exists.

✔ No duplicated requirements exist.

✔ All sections completed.
