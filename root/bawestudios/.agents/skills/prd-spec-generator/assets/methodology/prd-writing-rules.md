# BAWE PRD WRITING RULES
Version: 1.0

## PURPOSE

This document defines HOW the LLM must think while generating a Product Requirements Document.

It is NOT a template.

It is NOT part of the final PRD.

It is an internal reasoning guide.

The objective is to guarantee that every PRD generated by BaWeStudio is:

- Consistent
- Complete
- Actionable
- Technically neutral
- Easy to implement
- Easy to validate

The PRD must become the single source of truth for every downstream skill.

---

# GOLDEN PRINCIPLE

Describe the PRODUCT.

Never describe the IMPLEMENTATION.

The reader must understand exactly what must exist without knowing how it will be programmed.

---

# THINKING ORDER

Always generate the document following this reasoning sequence.

Never change the order.

1. Understand the business.

2. Understand the users.

3. Understand the problem.

4. Define the product.

5. Define the complete product scope from the client's essential functions.

6. Define the future.

Never start by listing features.

Features are consequences of solving problems.

---

# SOURCE OF TRUTH

Every requirement must originate from one of these sources:

✓ Client interview

✓ project-context.md

✓ Explicit business logic

✓ Industry standard expected by the selected project type

Never invent requirements outside these sources.

---

# REQUIREMENT GENERATION

Every functional requirement must answer:

Why does this feature exist?

Who needs it?

What business value does it generate?

Can the application work without it?

If no business value exists...

Do not include the feature.

---

# USER FIRST

Never write features first.

Always think in this order:

User

↓

Need

↓

Problem

↓

Flow

↓

Feature

↓

Acceptance Criteria

↓

Implementation (later pipeline)

If the order is reversed, rewrite the section.

---

# BUSINESS LANGUAGE

Write for stakeholders.

Not for programmers.

Use business language.

Avoid implementation language.

GOOD

"The customer can schedule appointments."

BAD

"Create AppointmentController."

GOOD

"The administrator manages products."

BAD

"Implement CRUD."

---

# TECHNICAL NEUTRALITY

The following concepts MUST NEVER appear.

Programming language

Framework

Database

REST

GraphQL

Docker

Kubernetes

Redis

RabbitMQ

Kafka

ORM

JWT

OAuth

Microservices

Cloud provider

API routes

Folder structure

Tables

Indexes

Anything related to implementation.

Those belong to Architecture.

---

# CLARITY

Each sentence must express only one idea.

Avoid paragraphs with multiple concepts.

Avoid nested requirements.

Prefer explicit statements.

---

# CONSISTENCY

If one section defines something...

Every following section must respect it.

Never contradict previous decisions.

Never rename entities.

Never create new actors later.

Never change terminology.

The same concept must always use the same name.

---

# complete product scope DISCIPLINE

The interview's priority answer is a priority build signal. It does not define
the complete product boundary by itself.

It is not a permission to reduce quality, ship a demo, expose test data or write
UI copy that speaks to the builder instead of the business user.

Complete product scope is derived from all product authority.

Move a capability to Deferred Scope only when it is unsupported, explicitly
postponed, contradictory, or blocked by an unresolved decision.

When quality, trust, usability or professional presentation is at stake, do not
remove the smallest coherent improvement needed to make the requested product
feel real and client-presentable.

---

# FEATURE DISCIPLINE

Every feature must satisfy all of these:

Solves a user problem.

Has business value.

Can be reviewed by the client as a real product.

Can be tested.

Has acceptance criteria.

Belongs to exactly one scope.

---

# NO FEATURE CREEP

Never add features because:

"They are common."

"They are modern."

"They could be useful."

"They may be needed later."

Everything added must be justified.

---

# WRITING STYLE

Use short paragraphs.

Use explicit titles.

Use bullet lists whenever possible.

Avoid marketing language.

Avoid adjectives.

Avoid subjective words.

Avoid unnecessary explanations.

The PRD is an engineering document.

Not a sales document.

---

# TERMINOLOGY

One concept.

One name.

Example:

Customer

Never later write:

Client

Buyer

User

Consumer

Unless they represent different actors.

---

# ACTORS

Every actor must have:

Goals

Permissions

Responsibilities

Main actions

Never mix actors.

Never merge responsibilities.

---

# FLOWS

Every user flow must have:

Start

Trigger

Actions

Decision points

Success

Failure

End

No incomplete flows.

No circular flows.

---

# ACCEPTANCE CRITERIA

Every feature must have measurable acceptance criteria.

Avoid subjective validation.

The result must be binary.

Pass or Fail.

Nothing in between.

---

# Deferred Scope

Never delete ideas.

If they are not required for complete product scope:

Move them.

Deferred scope exists only for ideas that are unsupported, explicitly postponed, or blocked by unresolved decisions.

---

# INTERNAL VALIDATION

Before finishing the PRD ask internally:

Does every feature solve a real problem?

Does every feature belong to someone?

Can the complete product be implemented?

Can the complete product be shown to a paying client without looking like
a test/demo environment?

Can QA validate every feature?

Can Architecture understand this document?

Can Backend start from this document?

Can Frontend understand user behavior?

If any answer is NO...

Rewrite before finishing.

---

# DOWNSTREAM THINKING

Remember:

This document will be consumed by:

Architecture

Backend

Frontend

Testing

QA

Deployment

Every ambiguity multiplies downstream.

Every clarification reduces implementation cost.

Write to minimize ambiguity.

---

# FINAL RULE

Do not try to impress.

Try to remove uncertainty.

A perfect PRD is not the one with the most pages.

A perfect PRD is the one after which every downstream skill knows exactly what to build.
